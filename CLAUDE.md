# CLAUDE.md — BrewLog

Ти — агент, який пише навчальний проєкт **BrewLog** (облік виробництва малої броварні) для курсу «Парадигма ООП» (ЛР 1–3). Працюють двоє розробників естафетою: спершу **B** (перша половина), потім **A** (друга половина); кожен дає тобі промти зі свого файлу `docs/prompts/PROMPTS_A.md` або `PROMPTS_B.md`.

**Джерело правди — `HANDOFF.md`.** Перед роботою прочитай потрібні розділи HANDOFF (архітектура §4, модель §5, формули §6, схема §7, контракти §8, UI §9). Опис проєкту — `docs/BrewLog-опис.pdf`; якщо він розходиться з HANDOFF, діє HANDOFF.

## Стек

- C# , **.NET 10**, WPF; SQLite (один файл `%LOCALAPPDATA%\BrewLog\brewlog.db`).
- Проєкти: `src/BrewLog.Domain` (net10.0), `src/BrewLog.Data` (net10.0), `src/BrewLog.UI` (net10.0-windows, WPF), `tests/BrewLog.Tests` (net10.0, xUnit).
- NuGet — **лише** зі списку HANDOFF §4.2: CommunityToolkit.Mvvm, ScottPlot.WPF (v5), QuestPDF, ClosedXML, Dapper, Microsoft.Data.Sqlite, BCrypt.Net-Next, xunit (+ runner, Test.Sdk, coverlet.collector). Нову бібліотеку не додавай — спитай розробника.
- `Nullable` і `ImplicitUsings` увімкнені, file-scoped namespaces, один публічний тип — один файл, namespace = шлях до папки.

## Команди

```bash
dotnet build                                   # має бути 0 помилок
dotnet test                                    # усі тести зелені
dotnet run --project src/BrewLog.UI -- --smoke # smoke-перевірка без показу вікон; код виходу 0 = OK, лог: %TEMP%/brewlog-smoke.log
```

- **Не запускай UI у звичайному режимі** (`dotnet run` без `--smoke`) — він блокує термінал. Інтерфейс руками перевіряє розробник за чек-листом із промту.
- Середовище — Windows, Claude Code працює через Git Bash; шляхи пиши з `/`.

## Архітектура — обов'язкові правила

1. **Domain** не посилається на Data, UI, WPF, SQL чи NuGet-бібліотеки. Інтерфейси репозиторіїв і сервіси (бізнес-логіка) — тут.
2. **Data** реалізує інтерфейси з Domain: Dapper + SQLite, BeerXML, PDF (QuestPDF), Excel (ClosedXML), BCrypt.
3. **UI** — MVVM на CommunityToolkit.Mvvm. Вікна й сторінки **не містять розрахунків і SQL**. Code-behind дозволений лише для: `InitializeComponent`, `PasswordBox`, малювання ScottPlot з даних ViewModel, дрібних суто візуальних речей.
4. ViewModel отримує залежності через конструктор; композиція — у `AppServices` (без DI-контейнера).
5. Окремі вікна відкриваються тільки через `WindowService`; повідомлення й підтвердження — тільки через `DialogService` (стилізований `MessageDialog`, не `MessageBox`).
6. Сервіси перевіряють дозволи (`ICurrentSession.Can(...)`) і кидають `DomainException` з українським повідомленням; ViewModel ловить `DomainException` і показує через `DialogService`.

## ООП — обов'язкові правила (на цьому тримаються ЛР 1)

- Чотири ієрархії з HANDOFF §5.1 — **Ingredient, BatchState, User, IbuFormula** — не згортати, не замінювати enum-ами.
- **Ніяких `switch`/`if` за типом інгредієнта, станом партії, роллю чи формулою поза фабриками.** Поведінка — через `override`. Дозволено лише в `IngredientFactory`, `BatchStateFactory`, `UserFactory`, `IbuFormulaFactory`.
- Узагальнені класи: `Repository<T> where T : class, IEntity`, `Stock<T> where T : Ingredient`, `StockEntry<T>`, `Recipe.IngredientsOf<T>()`.
- Інкапсуляція: колекції назовні — `IReadOnlyList<T>`, зміна — через методи (`AddIngredient`, `AddMeasurement`), валідація всередині класу.
- Формули й еталонні значення — HANDOFF §6. Не вигадуй інших коефіцієнтів.

## Дані

- Схема — **тільки** в `src/BrewLog.Data/Infrastructure/Schema/schema.sql` (EmbeddedResource), `CREATE TABLE IF NOT EXISTS`. Колонки `snake_case`, `Dapper.DefaultTypeMap.MatchNamesWithUnderscores = true`.
- Кожне з'єднання: `PRAGMA foreign_keys = ON;`. Вставка: `INSERT ...; SELECT last_insert_rowid();`.
- Дати — `DateTime`, у БД `TEXT` ISO-8601 (`"o"` або `yyyy-MM-dd HH:mm:ss`). `DateOnly` не використовувати.
- Фізичні величини — `double`, гроші — `decimal` (у БД `REAL`).
- Поліморфні об'єкти (інгредієнти, стани, користувачі) мапляться з `Rows/*Row` через фабрики — Dapper не створює їх напряму.
- Сідери (`Seed/`) працюють лише для нової БД, дати рахують від переданого `today`. Змінив схему чи сідери → запиши в журнал стану «⚠ видаліть brewlog.db».
- Операції з кількох змін (списання сировини, розлив, збереження рецепта з рядками) — в одній транзакції.

## Інтерфейс (стиль «як Дія», палітра «Темне пиво»)

- Тільки ресурси з `src/BrewLog.UI/Themes/*.xaml`; **жодних hex-кольорів, шрифтів і розмірів у розмітці сторінок**. Бракує стилю — додай його в тему.
- Ключові стилі: `Card` (біла картка, радіус 24), `DocCard` (градієнтна «документ-картка»), `PrimaryButton` (темна «пігулка»), `SecondaryButton`, `TextButton`, `IconButton`, `InputBox`, `InputCombo`, `PageTitle`, `PageSubtitle`, `SectionTitle`, `Caption`, `Chip` (+ кольори етапів), `CleanDataGrid`, `ListRowCard`. Точний список — у `Themes/Controls.xaml`.
- Тексти інтерфейсу — **українською**, без англіцизмів там, де є нормальне українське слово. Числа: OG/FG — 3 знаки (`1,048`), ABV — 1 знак з `%`, IBU і SRM — цілі, гроші — `0,00 грн`. Культура `uk-UA`.
- Кнопки без дозволу — **приховані**.
- ScottPlot 5: `WpfPlot` у XAML, малювання в code-behind з даних ViewModel; дати по осі X — `DateTime.ToOADate()` + `Plot.Axes.DateTimeTicksBottom()`; для кирилиці задай шрифт (наприклад `Plot.Font.Set("Segoe UI")`); фон і кольори — з палітри; після змін `Refresh()`.
- QuestPDF: `QuestPDF.Settings.License = LicenseType.Community;` на старті; шрифт `Segoe UI` для кирилиці.
- Кожне нове вікно/сторінку **додай у `SmokeRunner`**.

## Код і коментарі

- Ідентифікатори — англійською (`RecipeCalculator`, `CanAdvance`). Коментарі й XML-doc — **українською**, коротко: `///` на кожному публічному класі й нетривіальному методі (що робить і навіщо, не переказ коду).
- Без закоментованого мертвого коду, без `TODO` без пояснення, без `async void` поза обробниками подій.
- Довгі операції (PDF, Excel) — `await Task.Run(...)` у ViewModel, кнопка вимикається на час виконання.

## Тести — повні, але прості

- Лише `tests/BrewLog.Tests` (net10.0). Покриваємо Domain, сервіси, BeerXML і кілька перевірок на тимчасовій SQLite. UI не тестуємо: XAML перевіряє smoke.
- Без пакетів для моків і тверджень (Moq, FluentAssertions тощо — **ні**) і без мережі. Залежності сервісів — власні заглушки в `tests/BrewLog.Tests/Fakes/`.
- Пиши сценарії з промту, а не добивай кількість. Орієнтир на весь проєкт — 70–80 тестових методів. Однотипні випадки — через `[Theory]`. Геттери й автовластивості не тестуй.
- Назви методів англійською: `Method_Condition_Result`; папки тестів повторюють теми Domain.
- Очікуване значення — літерал із HANDOFF §6 або пораховане вручну, а не та сама формула, що в коді. Тест упав — спершу звір із HANDOFF: еталон під код не підганяй.
- Порівняння дробових — лише з допуском: `Assert.Equal(1.0125, fg, 0.0001)`. Варіант із `precision` округлює обидва значення й дає хибні падіння на межі.
- Час у тестах — фіксована дата. Domain не читає системний годинник: `now` передається параметром, сервіси беруть `IClock`.
- BeerXML і формати чисел перевіряй під культурою `uk-UA`: CI працює під іншою й не покаже проблему з десятковою комою.
- SQLite: кожен тест має власний тимчасовий файл (xUnit запускає класи паралельно), `Pooling=False`, шлях — через конструктор, без статичного стану. Файл видаляй у `Dispose`.
- Покриття: `dotnet test --collect:"XPlat Code Coverage"`.
